## PLAT-01. Керування користувачами: `fuzzhelm user add | list | set-role`
- **Що в спеці:** §8.1 — JWT і 4 ролі; §12.9 — агент не вводить креденшлів, облікові записи створює людина. Інструменту
  створення користувачів брифінг не описує; до хвилі 3 в `user_guide.md` був python-heredoc із `input()`/`getpass`, який
  писав у `app_user` **без запису в `audit_log`**.
- **Що насправді:** користувача можна було створити лише кодом, повз аудит; роль міняли так само.
- **Що зробив:** підкоманда `fuzzhelm user` (`docs/api/cli.md`). Пароль — лише `getpass` двічі або `--password-stdin`;
  прапорця `--password` немає (argv видно в `ps` та історії); без термінала й без `--password-stdin` — exit 2. Правила:
  ≥ 8 символів (NIST SP 800-63B), ≤ 72 байти UTF-8 (межа bcrypt), без керівних символів, ≠ логіну. Хеш — bcrypt 12 через
  `UserRepo`. Кожна дія й її `audit_log` (`user.create`, `user.set_role`, `user.list`) — одна транзакція; `user_id =
  NULL`, `after._actor = {"login": "cli", "role": null, "os_user": …}`. `set-role` на ту саму роль не пише нічого;
  останнього `admin` понизити не можна. Гонку дубля ловить `UNIQUE(login)` — назовні лише «already exists» без SQL і
  параметрів (там був би bcrypt-хеш). Демо-адміністратора в робочій БД **не створено** — це крок **[ЛЮДИНА]**
  (`uv run fuzzhelm user add --login <логін> --role admin`, `docs/manuals/user_guide.md` §5); `app_user` робочої БД
  на 2026-09-19 порожня (`select count(*) from app_user` = 0).
- **Чим обґрунтовано:** STRIDE S/R — зміна складу користувачів і ролей має слід; пароль не лишає слідів поза bcrypt.
  `user.list` теж аудитується, бо так вимагала постановка хвилі («each writes audit_log»): перегляд облікових записів —
  чутлива дія. Тести: 7 unit-функцій / 12 випадків (`tests/unit/test_cli.py`, репозиторії в пам'яті) + 8 нових випадків
  `test_parser_rejects_bad_arguments` + 3 integration (`tests/integration/test_cli_db.py`, зокрема вхід створеного
  користувача через `/auth/login`).

## PLAT-01a. Незалежне рев'ю PLAT-01: відлуння пароля через `--password-stdin` і гонка «останнього admin»
- **Що в спеці:** постановка хвилі 3 — пароль «never echoed or logged»; PLAT-01 — «останнього admin понизити не можна».
- **Що насправді (знайдено рев'ю 2026-09-19):** (1) argparse за замовчуванням приймає скорочення довгих прапорців, тож
  `fuzzhelm user add --login a --role admin --password` (природна здогадка людини, прапорця `--password` немає)
  розбирався як `--password-stdin` (перевірено `build_parser().parse_args(...)` → `password_stdin=True`), а
  `--password-stdin` на терміналі читав рядок через `readline()` — **з відлунням**, без підказки; набраний пароль лишався
  на екрані. (2) `set-role` рахував адміністраторів звичайним SELECT: дві паралельні транзакції (READ COMMITTED), що
  понижують двох різних admin, обидві бачили «admin двоє» і разом лишали систему без адміністратора.
- **Що зробив:** (1) `--password-stdin` вимагає каналу: якщо stdin — термінал, exit 2 з підказкою запустити без
  прапорця (тоді `getpass` без відлуння), зі stdin не читається жоден символ; для `user add|list|set-role`
  `allow_abbrev=False` — `--password`/`--pass` тепер помилка розбору. (2) Новий `UserRepo.admins_for_update()`
  (`SELECT … WHERE role = 'admin' ORDER BY id FOR UPDATE`): пониження admin блокує рядки всіх адміністраторів до COMMIT;
  друга транзакція чекає, а PostgreSQL перечитує умову для оновлених рядків і бачить меншу множину. Якщо поки чекали, роль
  самої цілі вже змінили, — exit 2 «changed concurrently», без зміни і без аудиту.
- **Чим обґрунтовано:** тести — 3 нові випадки `test_parser_rejects_bad_arguments` (`--password`, `--pass`,
  `user list --js`), `test_user_add_password_stdin_on_terminal_is_refused_not_echoed`,
  `test_user_set_role_rechecks_target_after_locking_admins` (unit) і
  `test_user_set_role_locks_admin_rows_against_concurrent_demotion` (integration: поки сесія CLI тримає блокування,
  друга сесія роллю fuzzhelm_app з `lock_timeout = 200ms` отримує SQLSTATE 55P03; після послідовних пониження
  `second` і спроби понизити `root` лишається рівно один admin). `FOR UPDATE` вимагає права UPDATE на `app_user`, яке
  роль `fuzzhelm_app` уже має (`set_role`). Решту PLAT-01 рев'ю підтвердило: пароль і bcrypt-хеш не потрапляють у
  вивід, журнали й `audit_log`; помилки СУБД — лише клас і SQLSTATE; у робочій БД `select count(*) from app_user` = 0.

## PLAT-02. docker-compose: спільний `./config` для api і worker; збирання й запуск у контейнерах
- **Що в спеці:** §9 — 4 сервіси в compose; PUT /risk/limits має діяти на воркер (гаряча заміна, W-відкрите).
- **Що насправді:** кожен контейнер мав власну копію `config/` з образу — зміна лімітів через API до воркера не доходила
  (зафіксовано в `docs/deviations.d/workers.md`, «Відкрите»). Образи api/worker ніколи не збиралися.
- **Що зробив:** `api` монтує `./config:/app/config` (rw: `FileLimitsStore` робить tmp → `os.replace` у цій теці) і
  `./data:/app/data:ro` (ставки фандингу для `POST /backtests` — той самий `dataset_hash`, що в CLI, API-15); `worker` —
  `./config:/app/config:ro`. Сервіс `db` не змінено: `docker compose config --hash db` = `db19a781…` = мітка
  `com.docker.compose.config-hash` контейнера `fuzzhelm-db-1`, тож compose його не перестворював. Додано `.dockerignore`
  (не передавати в контекст `.env`, `.venv` ~429 МБ, `.git`, тести, документацію): контекст збірки — 15.57 МБ.
  Dockerfile виправлень не потребував. Результати запуску — `docs/manuals/deployment.md` §3a.
- **Середовище (не репозиторій):** перша `docker compose build` зависла на `load metadata for docker.io/library/
  python:3.12-slim` (понад 10 хв): процес `docker-credential-desktop get` не відповідав у неінтерактивній сесії
  (`~/.docker/config.json` має `"credsStore": "desktop"`). Збирав із тимчасовим `DOCKER_CONFIG` без credsStore
  (`{"auths": {}}` + посилання на `~/.docker/cli-plugins`, `DOCKER_HOST=unix://$HOME/.docker/run/docker.sock`) —
  публічні образи облікових даних не потребують; налаштування користувача не змінено.
- **Чим обґрунтовано:** один файл лімітів для API і воркера — умова гарячої заміни; воркер не пише в `config/`, тож ro.
  Рев'ю (2026-09-19) перевірило механізм, від якого залежить гаряча заміна: `docker compose run --rm --no-deps -T api`
  записав пробний файл у `/app/config` тим самим способом, що `FileLimitsStore` (`mkstemp` у тій самій теці → `fsync` →
  `os.replace`), двічі (v1, потім v2), а паралельно запущений `docker compose run -d --rm --no-deps worker` читав той
  самий шлях кожні 0.5 с: 10 зчитувань «absent» → 6 «v1» → 7 «v2», тобто заміна інода видна воркеру одразу (bind-mount
  теки, а не файлу); `touch /app/config/x` у worker → «Read-only file system». Пробний файл видалено.
  Наскрізну перевірку «PUT /risk/limits у контейнері → воркер перечитав» **не виконано**: у робочій БД немає адміністратора
  (PLAT-01, [ЛЮДИНА]). Прогони з контейнера мають `run.git_sha = NULL` (у образі немає `.git`; SHA бере
  `backtest.manifest` через `git rev-parse` — відкрите питання власнику `backtest`). Перевірено спільність файлу:
  sha256 `config/risk_limits.yaml` однаковий на хості й в обох контейнерах (`a5d212b57856aec9…`), у api тека rw, у worker — ro (`touch` → «Read-only file system»).

## PLAT-03. `GET /risk/events`: `until_ns` і keyset-курсор (ts, id) замість «найновіші ≤ 2 000»
- **Що в спеці:** §8.1 — «`/risk/events` — журнал вердиктів»; розмір і пагінація не задані.
- **Що насправді:** маршрут віддавав лише найновіші ≤ 2 000 записів (є `since_ns`, немає верхньої межі й сторінок): у
  прогоні з 26 979 записами ризику ранні VETO MaxDailyLoss через API були недосяжні (workers, «Відкрите»).
- **Що зробив:** відповідь — конверт `RiskEventPageOut {run_id, items, page_size, next_cursor}` (як `CandlePageOut` у
  `/market/candles`); порядок `ts DESC, id DESC`; `since_ns` (включно), `until_ns` (виключно), `cursor = "<ts_ns>:<id>"`,
  `limit` 1…2 000 (за замовчуванням 500). Маршрут бере `limit + 1` рядків, тож порожньої останньої сторінки не буває.
  `only=veto`/`only=transitions` тепер теж підкоряються вікну, `rule` і курсору (раніше `veto` ігнорував `since_ns` і
  `rule`, `transitions` — усе). Межі в нс → мікросекунди колонки з округленням **угору** (інакше `until_ns` з
  «хвостом» наносекунд губив рядки своєї мікросекунди — це ловить інтеграційний тест). Новий метод
  `RiskEventRepo.page_for_run`; `list_for_run` без змін (його використовує планувальник).
- **Замір на робочій БД (лише SELECT, скрипт у робочій теці сесії над `RiskEventRepo.page_for_run` з логікою
  маршруту):** прогін `89619416-720b-4880-b4e4-26d2c74bca68` — 26 979 записів `risk_event`, 14 сторінок по ≤ 2 000,
  26 979 унікальних id, 0.456 с на весь прохід; `until_ns = 2026-08-07T00:00Z` + `rule=max_daily_loss` + VETO дали 82
  записи = SQL `count(*)`, перший — observed −0.020578 (−2.058 %), як у `user_guide.md` §3.
- **Чим обґрунтовано:** OFFSET на журналі, що дописується, дублює й губить записи; keyset (ts, id) стабільний і
  використовує індекс `ix_risk_run_ts`. **Несумісність:** тіло відповіді було масивом — тепер об'єкт. Споживачів у коді
  немає (UI ще не написано); тести e2e/integration оновлено.
- **Поза переліком файлів компонента:** додано метод `MemRisk.page_for_run` у `tests/helpers/api_fakes.py` — реалізацію
  в пам'яті того самого репозиторію, без якої e2e-тести API не бачили б нового методу (зміна лише додає метод).

## PLAT-04. JWT: python-jose → PyJWT
- **Що в спеці:** JWT HS256, 8 год (§8.1); `pip-audit` (фаза 9). API-13: `ecdsa` 0.19.2 (PYSEC-2026-1325) тягне
  `python-jose`.
- **Що зробив:** `api/auth.py` — `import jwt` (PyJWT 2.14.0): `jwt.encode(..., algorithm="HS256")`,
  `jwt.decode(..., algorithms=["HS256"], issuer="fuzzhelm", leeway=0, options={"require": [8 claims], verify_exp/nbf/
  iat: False})`; час (`exp` без допуску, `iat`/`nbf` із допуском 30 с на розсинхронізацію) перевіряє код за
  ін'єктованим `Clock`, як і раніше. Нове: усі 8 claims обов'язкові, `uid/exp/iat/nbf` — лише цілі; «майбутній» `iat`
  теж відкидається. Тести: `test_token_with_other_algorithm_or_alg_none_is_rejected` (alg=none без підпису, з підписом,
  у різних регістрах, згенерований самою PyJWT; HS384/HS512 тим самим ключем; RS256/ES256; заголовок без alg),
  `test_claims_are_required_and_typed`; решту auth-тестів переписано з `jose` на `jwt` без послаблення. Тестові ключі
  «чужого» підпису подовжено до ≥ 32 байт, а для HS384/HS512 тим самим ключем стоїть фільтр
  `InsecureKeyLengthWarning` — попередження PyJWT про довжину ключа тут очікуване.
- **Чим обґрунтовано / що лишилось:** залежність `python-jose` у `pyproject.toml`/`uv.lock` лишається (файли провідного
  розробника); `uv tree --invert --package ecdsa` досі: `ecdsa v0.19.2 ← python-jose v3.5.0 ← fuzzhelm`. Рекомендація
  PYSEC-2026-1325 зникне з `pip-audit` після `uv remove python-jose` — це зробить провідний розробник; `uv tree --package
  pyjwt` залежностей не має. PyJWT валідує формат `sub`/`jti` (рядки) — наші токени це задовольняють.

## PLAT-05. MLP-автокодувальник (§5.17): навчання на справжньому IS-вікні замість 3 000-барної фікстури
- **Що в спеці:** «`MLPRegressor(hidden=(3,), max_iter=500, random_state=seed)` навчається на векторі x **нормальних
  барів IS-вікна** … ROC-AUC на розмічених ін'єкованих аномаліях — таблиця у звіті»; §3 — «MLPRegressor(8-3-8)».
- **Що насправді (до хвилі 3):** таблиця `docs/figures/quality_mlp_rocauc.md` була на 3 000 барах фікстури
  (DATA-12, WS-02: 0.9873 для 8-3-8 проти 0.9796 для 5-3-5).
- **Що зробив:** процедуру винесено в `quality/anomaly_eval.py` (unit-тест на малих даних, 0.59 с), скрипт читає з
  робочої БД дні 1–15 BTCUSDT — ті самі 21 600 барів, що й калібрування МФ (`dataset_hash 9156616d…` збігся з
  `data/calibration_manifest.json`), held-out — дні 16–20 (7 200 барів, OOS першого фолду). «Нормальні» бари = справжні
  бари без ін'єкцій, без порушень структурних інваріантів і не синтетичні (вилучено 0; синтетичних у вікні 0).
  Ін'єкції: 4 типи × 144 позиції (частота 0.02 на тип, разом 576 позитивних на 7 200 негативних), амплітуди як раніше.
  Команда: `uv run python scripts/train_anomaly_mlp.py` (10.2 с).
- **Результат (seed 20260918):** ROC-AUC по всіх типах **8-3-8 — 0.9531, 5-3-5 — 0.9729**; FPR при q₉₉ на чистих
  held-out барах 0.0375 / 0.0233 (номінал 0.01). По 6 seed: 0.9551 ± 0.0021 проти 0.9718 ± 0.0021, 8-3-8 програє у 6 з 6.
  Найбільша різниця — «товстий палець» (0.8772 проти 0.9196) і сплеск обсягу (0.9365 проти 0.9735).
- **Чутливість (не в закоміченому звіті, вивід у робочу теку сесії):** `--is-days 12 --holdout-days 3` (навчання 1–12,
  held-out 13–15, лише IS-вікно): 0.9540 проти 0.9773, по 6 seed 0.9567 ± 0.0038 проти 0.9792 ± 0.0045, FPR 8-3-8 —
  0.0433. Отже перевага 5-3-5 — не лише наслідок зміни режиму. `--from-fixture --rate 0.125` відтворює старі числа
  фікстури: 0.9873 / 0.9796 (price_spike 5-3-5 — 0.9997 замість 0.9998 через інший порядок генерації амплітуд).
- **Чому FPR > 1 %:** held-out потрапив на зміну режиму — σ(Δlog p) 0.000976 проти 0.000308 на IS (×3.17), 10.86 %
  чистих held-out барів виходять за центральні 99 % IS за Δlog p (таблиця дрейфу у звіті). Окремий замір денної σ
  1m-доходностей (скрипт у робочій теці сесії): дні 1–15 — 0.000116…0.000426, дні 16–20 — 0.000549…0.001423, на день 16
  припадає хвилинний рух 3.95 %; закриття на початку дня 16 — 64 705.7, на початку дня 20 — 77 134.2. Δlog p — єдина ознака брифінгу, не нормована волатильністю.
- **Чим обґрунтовано / відкрите:** WS-02 (`docs/deviations.d/ingest_ws.md`, не моя зона) стверджує, що вибір 8-3-8
  «підтверджено заміром»; на справжньому IS-вікні замір каже протилежне. Архітектуру я **не міняв**: вибирати її за
  held-out — підгонка під тестову вибірку, а назва 8-3-8 — із заготовленої відповіді комісії (§3). Рішення за автором:
  (а) лишити 8-3-8 і чесно навести обидва числа; (б) перейти на 5-3-5 (вектор §5.17 дослівно); (в) нормувати Δlog p
  на ATR, щоб прибрати залежність від режиму, і переміряти. Текст WS-02 варто оновити власнику `ingest_ws`.
