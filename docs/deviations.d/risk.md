# Розходження «спека ↔ реальність»: модулі `sizing` і `risk`

Формат: **що в спеці / що насправді / що зробив / чим обґрунтовано**. Усі числа нижче обчислено кодом
і закріплено тестами (назви тестів у дужках).

## R-01. Стала часу фільтра 1-го порядку: «γ = 0.2 ⇒ T = 4Δt»
- **Спека (§5.8, тест I `test_first_order_filter_reaches_63pct_in_T`):** фільтр `s_t = s_{t−1} + γ(s* − s_{t−1})`
  з γ = 0.2 має T = 4Δt, тобто досягає 63.2% сходинки за 4 бари.
- **Насправді:** перехідна характеристика дискретного фільтра `1 − (1−γ)^n`: після 4 барів — 59.04% (< 63.2%),
  після 5 — 67.23%. Точна стала часу (еквівалент полюса `e^{−Δt/T} = 1−γ`) — `T = −Δt/ln(1−γ) ≈ 4.4814Δt`.
  Число 4 — стала часу неперервного прототипу при дискретизації зворотним Ейлером `γ = Δt/(T+Δt)` ⇒
  `T = (1−γ)/γ·Δt`; прямий Ейлер дав би 5Δt.
- **Зроблено:** тест із назвою брифінгу перевіряє правду (59.04% < 63.2% ≤ 67.23%; `τ = −1/ln 0.8`;
  `1 − 0.8^τ = 1 − e^{−1}`; походження числа 4). Функції `filter_time_constant_bars`,
  `backward_euler_time_constant_bars` у `sizing/vol_target.py`.
- **Обґрунтування:** у звіті формулювати «T ≈ 4.5Δt (точно −Δt/ln 0.8); 4Δt — неперервне наближення».

## R-02. Тест Купця: «відкидає при 20 пробоях із 500»
- **Спека (§10 J, `test_kupiec_rejects_at_20_breaches_of_500`):** 20 пробоїв на W = 500 при p = 0.05 → відкидання.
- **Насправді:** LR(20; 500, 0.05) = **1.1267 < χ²₁(0.95) = 3.8415** ⇒ модель НЕ відкидається. Область
  неприйняття на W = 500: x ≤ 16 (LR(16) = 3.888) або x ≥ 36 (LR(36) = 4.511); прийнятні x ∈ [17; 35].
  Для порівняння: на W = 250 ті самі 20 пробоїв відкидаються (LR = 4.040), прийнятні x ∈ [7; 19] —
  можливо, приклад брифінгу походить із вікна 250 (це припущення, не перевірене джерело).
- **Зроблено:** формулу не змінено; тест із назвою брифінгу стверджує `reject is False` і звіряє LR з
  незалежним обчисленням через біноміальні log-pmf (`math.lgamma`), плюс межі області (17, 35).
- **Обґрунтування:** наукова чесність — підгонка формули під очікуваний результат заборонена брифінгом (§0.2).

## R-03. Ціна відсутності гістерезису: «−1.15% капіталу на добу»
- **Спека (§5.9):** 1440 барів/добу × 2 комісії × 0.04% = −1.15% капіталу на добу.
- **Насправді:** 1440 × 2 × 0.0004 = **1.152** частки номіналу, тобто **115.2%** на добу при номіналі 1×E
  (помилка одиниць на два порядки). Компаратор без петлі на сигналі, що тремтить біля порогу (0.26/0.24),
  дає 1 виконання на бар — 57.6%/добу; тригер Шмітта на тій самій послідовності — 1 виконання за добу.
- **Зроблено:** `test_hysteresis_absence_cost_matches_brief_arithmetic` стверджує 1.152 і НЕ 1.15%;
  виправлено докстрінг `sizing/hysteresis.py`.
- **Обґрунтування:** висновок брифінгу (гістерезис необхідний) від виправлення лише посилюється; у звіті
  подати правильне число.

## R-04. «Інваріант: CVaR ≥ VaR ≥ 0» і оцінювач квантиля
- **Спека (§5.13):** `VaR₉₅ = −Quantile_{0.05}`, `CVaR₉₅ = −(1/m)Σ_{i≤m} r_(i)`, m = ⌊0.05W⌋; CVaR ≥ VaR ≥ 0.
- **Насправді:** (а) схема інтерполяції квантиля не зафіксована, а від неї залежить, чи CVaR ≥ VaR для кожної
  вибірки; (б) `VaR ≥ 0` не тотожність — на вікні, де r_(m) > 0 (≥ W − m + 1 додатних дохідностей), VaR < 0.
- **Зроблено:** квантиль — нижня емпірична оцінка `r_(m)` із тим самим m, що й у CVaR (для W = 500 збігається з
  `numpy.quantile(method="lower")`); тоді CVaR ≥ VaR для будь-якої вибірки. CVaR рахується як
  `VaR + mean(r_(m) − r_(i))` — математично те саме, що `−mean`, але нерівність зберігається і в float
  (пряма `−mean` на однакових значеннях може бути на 1 ulp нижча за VaR). `test_cvar_ge_var_always` (property)
  + `test_var_can_be_negative_on_all_gain_window` документує, що VaR ≥ 0 не гарантовано.
- **Обґрунтування:** у звіті інваріант формулювати як «CVaR ≥ VaR»; «VaR ≥ 0» — лише для вікон із досить
  частими збитками.

## R-05. Інтерпретація `max_position_notional: {value: 0.30, unit: equity_fraction}`
- **Спека (§7):** «0.30 частки капіталу» без уточнення, чого саме.
- **Насправді:** буквальне «номінал позиції ≤ 0.30·E» робить недосяжним `max_gross_leverage = 3.0` (одна позиція
  ≤ 0.3×) і перекриває vol-target сайзер щоразу, коли `s_t > 0.3`, тобто для будь-якого σ_ann < σ_target/0.3 ≈ 0.667.
- **Зроблено:** ліміт — **початкова маржа позиції ≤ 0.30·E**: `|q|·P / L_set ≤ 0.30·E`, де `L_set` — біржове
  плече позиції (`RiskContext.leverage_setting`, за замовчуванням 3 = `instrument.max_leverage` з DDL). При L_set = 3
  номінал ≤ 0.9·E; `MaxGrossLeverage = 3.0` стає досяжним при L_set ≥ 10 або ≥ 4 позиціях — тобто це запобіжник.
  `test_max_position_notional_is_margin_fraction_of_equity`.
- **Обґрунтування:** маржа — те, що позиція реально «займає» з капіталу й що втрачається при ліквідації
  ізольованої позиції; тож ліміт обмежує найгірший збиток на позицію 30% капіталу і лишає інші ліміти змістовними.

## R-06. LiquidationBufferGuard: `L'_max` сам по собі не відновлює DTL ≥ 6
- **Спека (§5.10):** ліміт DTL ≥ 6; при порушенні — зменшити плече до `L'_max = 1/(Δ_stop/(P_e(1−b)) + mmr)`.
- **Насправді:** `L'_max` гарантує, що стоп спрацює раніше за ліквідацію із запасом b, але відстань до ліквідації
  після нього ≈ Δ_stop/((1−b)(1−mmr)); при Δ_stop = χ·ATR = 2·ATR це ≈ 2.51·ATR < 6·ATR — ліміт лишався б порушеним.
- **Зроблено:** плече обмежується `L_cap = min(L'_max, L_DTL)`, де `L_DTL` — плече, за якого DTL = 6 рівно
  (закрита форма `max_qty_for_dtl`); приріст стискається SHRINK-ом, VETO — лише якщо навіть незмінна частина
  позиції вже за межею. P_liq рахується для пост-трейдової позиції на крос-маржі: W = E − N_інших·mmr, вхід = P_t
  (точна тотожність, доведена в докстрінгу `risk/margin.py`). У payload — обидві межі й `cap_binding`.
  `test_liquidation_guard_reduces_leverage_before_veto` + property `test_guard_approved_position_satisfies_every_limit`.
- **Обґрунтування:** після «ремонту» виконуються обидві умови; при широкому стопі (> 4.8·ATR) вузьким місцем
  стає саме формула брифінгу (Δ_stop > 6·(1−b)·(1∓mmr)·ATR ≈ 4.8·ATR).

## R-07. Сцена демо 2:30–3:20: «4% → WARNING, 8% → COOLDOWN, 12% → HALTED» при flash_crash
- **Спека (§15, §5.12):** просадка 4/8/12% послідовно переводить автомат у WARNING/COOLDOWN/HALTED.
- **Насправді:** при падінні в межах однієї UTC-доби PnL_day ≈ −DD, тож денні пороги спрацьовують раніше:
  −2% → COOLDOWN, −3% → HALTED (за DD лише 2% і 3%). Сходинки 4/8/12% можливі лише, якщо падіння розтягнуте на
  кілька діб. `test_intraday_crash_hits_daily_limits_before_drawdown_thresholds`.
- **Зроблено:** логіку автомата не змінено (обидві умови — з §5.12). Для авторів демо/реплею (хвиля 2):
  або сценарій, розтягнутий на кілька UTC-діб, або чесно показати «HALTED за денним лімітом −3%».
- **Обґрунтування:** це наслідок самої конфігурації, а не дефект коду.

## R-08. Автомат станів: уточнення, яких немає в §5.12
- **Шість подій** (`HALT_BREACH, COOL_BREACH, WARN_BREACH, RECOVERY, STEADY, ADMIN_RELEASE`) класифікуються
  відносно поточного стану з пріоритетом згори донизу; таблиця 4×6 — явний dict, тотальна (24 клітинки).
- **dwell** — кількість барів у поточному стані (скидається лише при зміні стану) — як колонка `risk_event.dwell_bars`.
- **Ескалація через рівень** (NORMAL → COOLDOWN/HALTED на гепі) — одразу; повернення — лише на рівень нижче.
- **WARNING → NORMAL** додатково блокується активним тригером WARN (σ_ann/σ_base > 1.6): інакше повернення
  в NORMAL на наступному ж барі знову давало б WARNING (чатеринг). У COOLDOWN тригер волатильності не діє.
- **Після зняття HALTED** — стан COOLDOWN (reduce-only, κ = 0.25), а пік і E_open перебазовуються на поточний
  капітал: без цього засувка спрацювала б знову на наступному барі (пласка книга не відіграє історичний пік).
- **σ_base** у брифінгу не визначено — `vol_ratio` передає викликач (напр. медіана σ_ann на IS-вікні).
- **kill-switch і HALTED** — одна засувка: `RiskStateMachine` містить `KillSwitch`; ручне `trip()` ⇒ HALTED,
  `release(Role.ADMIN)` пише два записи аудиту (`killswitch.release`, `risk.release`) зі станом до/після.

## R-09. Гістерезис: «вихід лише при |u| < 0.12»
- **Спека (§5.9):** вихід при `|u_final| < 0.12`.
- **Насправді:** буквальне `|u|` тримало б лонг при u = −0.20 (сигнал проти позиції).
- **Зроблено:** вихід знаковий — лонг тримається, доки `u ≥ 0.12`; розворот — лише на рівні входу `|u| ≥ 0.25`.
  Послідовність брифінгу 0.30 → 0.20 → 0.15 → 0.11 дає LONG, LONG, LONG, FLAT (як і очікувалося).

## R-10. Відхилення сигнатур від `docs/contracts.md` §10–§11
- `VolTarget(...)` — усі параметри keyword-only (правило ruff PLR0917, > 5 позиційних); те саме для
  `margin_ratio(..., *, maint_amount)`, `side_liq_price(..., *, maint_amount)`, `max_qty_for_dtl(side, *, ...)`.
- `Verdict(kind, factor)` — `factor: Fraction` (точний); для журналу/БД — `Verdict.factor_dec: Decimal` (floor 1e-18).
- `RuleVerdict` має додаткове поле `halt: bool`; `observed`/`limit` можуть бути `None` (невизначене спостереження).
- `RiskGuard` додає до шести лімітів сьомий запис `risk_mode` (гейт режиму COOLDOWN/HALTED/kill-switch).
- `RiskStateMachine.update(obs)` приймає `RiskObservation(ts_ns, equity, vol_ratio)`; DD і денний PnL рахує
  вбудований `EquityTracker`.
- Фактичний API — `docs/api/risk.md`.

## R-11. `action: shrink` без місця для приросту
- **Спека:** MaxPositionNotional / MaxGrossLeverage мають дію `shrink`.
- **Насправді:** SHRINK(f) визначено лише для f ∈ (0; 1) строго; коли місця немає зовсім (f → 0), правило
  повертає VETO (для приросту; редукція дозволена завжди).

## R-12. Оцінка швидкості просадки
- **Спека (§5.12):** `n_min ≥ (DD_max − DD₀)/v_max(COOLDOWN)` — «оцінка гіршого випадку, не доведення стійкості».
- **Зроблено:** `per_bar_loss_bound`, `min_bars_to_drawdown` із явним переліком припущень у докстрінгу
  (стоп без гепу понад κ_slip, ρ_base — бюджет усієї книги, κ_mode незростає за DD). Тест звіряє межу з
  гіршим допустимим шляхом; жодних тверджень про стійкість код і документація не роблять.
