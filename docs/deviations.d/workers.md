# Розходження «спека ↔ реальність»: `workers` (торговий і ingest-воркери, запис прогонів, демо)

Формат: **що в спеці / що насправді / що зробив / чим обґрунтовано**. Кожне число — з прогону, команду вказано.
Робоча БД — `postgresql+asyncpg://fuzzhelm:fuzzhelm@localhost:5442/fuzzhelm`, тестова — порт 5443.

## W-01. Торговий воркер споживає лише kline + markPrice
- **Спека (§4.1):** один потік `WS(kline_1m, aggTrade, depth20@100ms, markPrice) → Normalizer → … → рішення`.
- **Насправді:** рішення будуються лише на закритих свічках; угоди потрібні детектору прогалин угод, а снапшоти книги —
  здоров'ю конвеєра й OBI, якого ядро не використовує. Нормалізація 25 912 снапшотів книги 45-хв сесії — основна вартість:
  конвеєр на всіх потоках — 5.41 с, на kline+markPrice+aggTrade — 1.36 с, на kline+markPrice — 0.16 с (скрипт-замір у
  робочій теці сесії над `fixtures/ws/btcusdt_2026-09-18.jsonl.gz`, `IngestPipeline.run`).
- **Зроблено:** торговий воркер споживає потоки з `feed.streams` профілю (`[kline, markPrice]`: свічки + біржовий час для
  детектора прогалин свічок); повний потік (усі 4, журнал, `ingest_gap`, `dq_score`) пише ingest-воркер. `ReplayFeed`
  отримав фільтр `streams`, який відкидає рядки за іменем потоку ДО розбору JSON (`ingest/replay.py: iter_items`):
  читання сесії з фільтром kline+markPrice — 0.11 с проти 0.25 с без фільтра.
- **Обґрунтування:** офлайн-e2e швидкий (весь `tests/e2e/test_replay_e2e.py` — 1.6–2.4 с), а Q торгового контуру
  рахується на тих подіях, які він справді споживає (на 45-хв сесії 0.9806 проти 0.9683 на всіх потоках — різниця від
  timeliness книги). Шлях «кадр → свічка» той самий код `IngestPipeline`.

## W-02. `dataset_hash` live/replay-прогону — ідентичність СЕСІЇ, а не лише даних
- **Спека (§6):** `run.dataset_hash NOT NULL`, `ux_run_identity (config_hash, dataset_hash, seed, engine, git_sha)`.
- **Насправді:** набір даних paper-прогону відомий лише в кінці; а два реплеї того самого файлу з тим самим конфігом і
  git_sha — різні прогони (ззовні приходять команди адміністратора, зміни лімітів), але мали б однакову ідентичність і
  другий упав би на `ux_run_identity`.
- **Зроблено:** `dataset_hash = BLAKE2b-256(canonical_json({feed, source, source_sha256, scenario, streams,
  warmup_dataset_hash, session_started_ns}))` (`trading_worker.session_dataset_hash`); самі складники — у першому записі
  журналу `session.start` (захищені ланцюгом). `config_hash` лишається `BacktestConfig.config_hash` профілю — порівнянним
  із бектестом. Перевірено: два прогони поспіль тієї самої сесії на тестовій БД — обидва DONE, та сама крива
  (`test_replay_worker_persists_run_with_full_passport`).
- **Обґрунтування:** сесія — подія в часі; «чиста» ідентичність даних не губиться (sha256 файлу, хеш прогріву в журналі).

## W-03. Профіль replay: `u_enter = 0.20` (клітинка сітки), а не 0.25
- **Спека:** e2e вимагає ≥ 1 угоди на записаній сесії; §15 — «спрацьовує угода → ExplainView».
- **Насправді (виміряно):** з дефолтним порогом 0.25 45-хв сесія не дає жодного входу: максимум |u_final| = 0.24270
  (`uv run python -m fuzzhelm.workers.trading_worker --profile replay --no-db --speed inf --param u_enter=0.25` →
  fills 0, `max_abs_u_final` 0.24270316816134185). Довший прогрів (1 500 і 2 981 бар замість 523) max |u| не змінює
  (0.243; скрипт-експеримент у робочій теці сесії).
- **Зроблено:** `config/profiles/replay.yaml: params: {u_enter: 0.20}` — значення з осі сітки `backtest.grid`
  (u_enter ∈ {0.20, 0.25, 0.30}); тоді 1 угода (вхід 19:32 за 81 134.70, вихід 19:35 за 81 089.30, −7.28 USDT).
  Paper і backtest лишаються з 0.25. `config_hash` replay-прогону тому інший, ніж у бектесту (чесно).
- **Обґрунтування:** це налаштування демо-профілю, а не підгонка результату: число — з сітки експерименту, угода збиткова,
  і розходження задокументоване. Робочу точку для звіту обирає фаза 7 з OOS-фронту Парето.

## W-04. Сценарій flash_crash: дизайн і фактична послідовність станів (≠ «4 % → 8 % → 12 %» §15)
- **Спека (§15, §17):** «просадка 4 % → WARNING, 8 % → COOLDOWN, у журналі MaxDailyLoss · VETO · observed −2.10 % ·
  limit −2.00 %, 12 % → HALTED»; сценарій доводить систему до HALTED без людини.
- **Дизайн (`scripts/make_demo_scenario.py`, W-15):** чиста сесія спершу проганяється шляхом демо; момент ін'єкції t₀ —
  межа хвилини, на яку стратегія ВХОДИТЬ у лонгу 0.066 BTC (вхід 81 134.70, стоп 81 012.20) — 2026-09-18 19:33:00 UTC.
  Від t₀ ціни всіх потоків × профіль: розрив −6.5 % саме на межі хвилини, −11 % за 20 с, −7.5 % до кінця хвилини, −3 %
  через 10 хв. Кадри до t₀ побайтово ті самі (тест). Розрив на межі хвилини — суть стрес-тесту: барний брокер виконує
  стоп усередині бару за рівнем (оптимістично), лише розрив крізь стоп перевіряє припущення §5.12 «про виконання стопа».
- **Насправді (виміряно, `uv run python scripts/demo_flash_crash.py`):** стоп виконано за open бару розриву
  (75 865.80 при open 75 862.20), капітал 9 997.94 → 9 648.11 (день −3.52 %) → **NORMAL → HALTED** (HALT_BREACH,
  19:33:59.999) — одним переходом, без WARNING/COOLDOWN; наступні 17 барів — HALTED, 0 виконань. Записів VETO — **немає**,
  зокрема MaxDailyLoss: після бару розриву бажаний бік = 0, намірів ЗБІЛЬШИТИ експозицію немає, а ризик-ланцюг
  (де живе MaxDailyLoss) викликається лише на намір (ENG-04). М'якший варіант (розрив −4.5 %, профіль
  `0:0.955,20000:0.93,60000:0.95,600000:0.975`; `make_demo_scenario.py --name flash_crash_mild --out-dir <tmp> --profile …`,
  далі воркер `--session`) дає NORMAL → COOLDOWN (капітал 9 755.17) і теж жодного наміру входу до кінця сесії
  (|u_final| < 0.20) — отже й жодного VETO MaxDailyLoss.
- **Чому поступова сцена брифінгу недосяжна:** кожна позиція має стоп 2·ATR, а розмір — ризик ρ·|u|·E на відстань стопа,
  тож збиток понад ~ρ·E можливий лише розривом крізь стоп, який позицію ж і закриває; COOLDOWN з пласкою книгою
  поглинаючий (ENG-14), а денні пороги (−2 %/−3 %) спрацьовують раніше за пороги просадки 8 %/12 % (див. також
  `journal.d/risk.md`). Поступові 4→8→12 % потребують відкритої позиції, що втрачає без спрацювання стопа.
- **Зроблено:** демо показує фактичну послідовність і пояснення; автоматичні тести
  `test_flash_crash_reaches_halted_without_human_input`, `test_halted_latches_until_admin_release` (офлайн) і
  `test_flash_crash_halts_on_db_and_only_admin_release_via_api_unlatches` (БД + справжній API).
- **Обґрунтування:** наукова чесність (§0.2): послідовність не підганяється під сценарій захисту.
- **Доповнення рецензента (запис VETO з observed/limit для акту §15 існує — у першому повному прогоні):** у прогоні
  `89619416-…` 82 записи `max_daily_loss · VETO` (усього VETO 3 753: ще 3 671 — `risk_mode`, вхід у COOLDOWN), перший —
  2026-08-04 22:57:59.999 UTC, `observed = −0.020577793768`, `limit = −0.02` (запит `select … from risk_event where
  run_id = '89619416-…' and rule = 'max_daily_loss' and verdict = 'VETO' order by ts`). Тобто рядок журналу, який
  описує брифінг («MaxDailyLoss · VETO · observed=−2.10 % · limit=−2.00 %»), система справді пише — коли після денного
  збитку ≥ 2 % є намір входу; на захисті його показує запит до `risk_event` (`docs/manuals/user_guide.md` §3), а не сцена flash_crash.

## W-05. Прогрів з історії, що передує потоку
- **Спека (завдання хвилі):** «warm-up from DB history preceding the feed start».
- **Насправді:** 45-денне вікно БД закінчується 2026-09-18 00:00, а записана сесія починається о 19:06 — між ними
  19 год без свічок; прогрів з дірою дав би ознакам стрибок.
- **Зроблено:** рівно `resolved_warmup()` = 523 бари `[first_open − 523 хв, first_open)` з БД; якщо їх немає або є дірки —
  запасне джерело (replay: записані рядки REST `fixtures/rest/binance_klines.json.gz`, `ts_ingest` = момент запису
  фікстури; paper: публічний REST `/fapi/v1/klines`), upsert у `candle` (src = REST) і повторне читання з БД.
  `trade_start = 523` — на прогріві рішень немає, кроки прогріву не пишуться (капітал пласкі 10 000). Перевірено: перший
  прогін на робочій БД підтягнув 523 бари з фікстури (`db+fixture`), наступні — з БД (`db`); paper 2026-09-19 — `db+rest`
  (1 запит klines).
- **Обґрунтування:** та сама історія, що бачила б біржа; «зараз» не вигадується.

## W-06. Лаг для StaleDataGuard у live
- **Спека (§5.11):** `StaleDataGuard(lag > 5 с ∨ Q < 0.90)`; рушій рахує `lag = ts_ns − last_data_ns`, де `ts_ns` —
  закриття бару (годинник барів).
- **Зроблено:** воркер передає `last_data_ns = close_t − max(0, now − ts_event закриття свічки)`, де `now` — годинник
  конвеєра (FrameClock реплею або SystemClock). Тоді «лаг» — фактична затримка обробки свічки (для REST-добраної після
  розриву — хвилини → VETO приросту). Q — скор поточної години конвеєра (`IngestPipeline.dq_scores()[-1]`).
- **Обґрунтування:** межа детермінізму рушія не порушується, а семантика «дані застаріли» — правдива.

## W-07. VaR₉₅/CVaR₉₅ у `equity_point`
- **Спека:** колонки `var95`, `cvar95 NUMERIC(38,18)`; §5.13 — історичні оцінки на вікні W = 500, звітна метрика.
- **Зроблено:** гроші (USDT): `E_t · VaR̂` з `risk.var.historical_var_cvar` на останніх min(t, 500) бар-дохідностях
  (вікно закінчується на t включно); NULL, поки дохідностей < 20. Пакетний шлях векторизовано блоками, покроковий —
  `RollingVar`; тест звіряє обидва з `risk.var` (≤ 1e−12) і CVaR ≥ VaR.
- **Обґрунтування:** колонки стоять поруч із капіталом у грошовому типі; частки лишаються в `risk.var` для тесту Купця.

## W-08. Журнал подій прогону зберігається (бектест, API, воркер)
- **Спека:** `event_journal` із ланцюгом; паспорт має `journal_head_hash`.
- **Насправді (API-08 п. 2):** рушій вів журнал з `keep=False` без стоку — у БД була лише голова.
- **Зроблено:** `run_backtest(..., journal_sink=…)`; `scripts/run_backtest.py`, `DbBacktestRunner` (POST /backtests) і
  воркер пишуть записи в `event_journal`. У live-прогоні ланцюг містить ще `session.start`, кожну спожиту свічку
  (`candle`), команди керування і `session.end`. Перевірено `fuzzhelm verify-journal`: перший повний прогін — 27 663
  записи, «chain OK, anchor OK» (голова = `run.journal_head_hash`).

## W-09. Ingest-воркер: журнал без рядка `run`, Q лише завершених годин
- **Спека:** `run.kind ∈ {backtest, paper, replay, grid_cell, testnet}`; «погодинний Q».
- **Зроблено:** журнал сесії інжесту має власний run_id (uuid4) без рядка `run` (як `replay-gap` CLI); `dq_score` пишеться
  лише для годин, що вже завершились за біржовим часом — незавершену пізніше повністю порахує `scheduler.hourly_dq`
  (рахує лише години без рядка, API-12). Димовий прогін 1.5 хв рядків `dq_score` не дав (завершеної години не було;
  Q незавершеної години 0.9738 / 0.9743 — лише у виводі і в події `health`).

## W-10. Колізія `client_order_id` між збереженими прогонами з тим самим seed (знайдено на робочій БД)
- **Було:** `TradingLoop` генерував id заявок `SeededIdGenerator(seed, b"fuzzhelm.engine")` — однакові для будь-яких
  прогонів з тим самим seed. `sim_order.client_order_id UNIQUE` ⇒ другий збережений прогін падав. Відтворено: реплей після
  бектесту (обидва seed 20260918) на робочій БД → `IntegrityError` на `sim_order_client_order_id_key`, прогін
  `fcf44bb4-…` записано FAILED. Той самий дефект мав POST /backtests для двох вікон з однаковим seed.
- **Зроблено:** `backtest.engine.run_order_ids(seed, run_id)` — простір імен з run_id; `run_backtest` вживає його, коли
  run_id передано (збережені прогони), воркер — завжди. Без run_id (сітка, тести рушія) — як було, тож тести рушія й
  equity_hash не змінились (перший прогін: `8a82f814…`, як у ENG). Тест
  `test_persisted_runs_with_same_seed_get_distinct_client_order_ids` + два прогони поспіль в інтеграційному тесті.
- **Наслідок для першого повного прогону (знайшов рецензент):** `89619416-…` записано ДО цього виправлення, тож його
  `client_order_id` — лише з seed (перша заявка `64d762cf-…`, та сама, що зламала `fcf44bb4`). Поточний код з тим самим
  run_id дає інші id (`ba5819a3-…`), а оскільки журнал містить заявки, голова журналу вже не відтворюється:
  `8cc9dd23f983a32f…` проти збереженої `a0c35dc58cb9f62e…` (перша розбіжність — seq 7, перша заявка). Крива капіталу
  відтворюється побітово (`equity_hash 8a82f814…` і з рушія, і з 64 800 рядків `equity_point`), `dataset_hash 3e58da26…`
  і `config_hash 7f91fc34…` перераховано незалежно (з БД і з `run.config`) — збігаються. Новий прогін з тією самою
  ідентичністю неможливий (`ux_run_identity` не бачить незакомічених змін: `git_sha` той самий 5fed0fd), тому
  `scripts/run_backtest.py` тепер при повторному запуску проганяє рушій поточним кодом і пише у звіт, що саме
  відтворюється (W-24). Після коміту хвилі 2 (новий git_sha) повторний запуск скрипта створить прогін, повністю
  відтворюваний закоміченим кодом.
- **Супутнє:** FAILED-прогін раніше отримував хеші і `session.end`, дописаний після відкоченого кроку, — ланцюг у БД мав
  дірку (`verify-journal`: `fcf44bb4…: 27 entries, chain BROKEN at seq 26`). Тепер FAILED-прогін хешів не отримує і
  журнал після збою не дописує — у БД лишається цілий префікс; текст помилки для СУБД — лише клас і SQLSTATE
  (`api.backtests.public_error`, API-16). Рядок `fcf44bb4` лишено як є — це чесна історія знахідки.

## W-11. Прапорець «брудного» дерева git
- **Спека:** `git_sha CHAR(40)`.
- **Зроблено:** SHA — HEAD; якщо дерево має незакомічені зміни, `run_metric.git_dirty = 1.0` (і в журналі `session.start`).
  Усі прогони цієї сесії мають git_dirty = 1 (HEAD 5fed0fd + незакомічена хвиля 2).

## W-12. Правки `backtest/engine.py` (цільові)
- `run_backtest(journal_sink=)` (W-08), `run_order_ids` (W-10);
- `release_halt` більше не губить `risk_event` переходу між барами: раніше `step()` очищав список записів на початку
  кроку, тож перехід HALTED → COOLDOWN, спричинений адміністратором між барами, не потрапляв у жоден StepResult (лише в
  EventJournal). Тепер — `take_pending_risk_events()` (воркер пише одразу) або StepResult наступного бару;
- `apply_risk_limits(tree)` — гаряча заміна секцій `limits` і `state_machine` (W-18).
Тести рушія (`test_trading_loop.py`, `test_backtest_engine.py`, `test_engine_property.py`) зелені.

## W-13. Правки storage (адитивні)
`order_values` + `OrderRepo.insert_many`, `position_values` + `PositionRepo.insert_many` (пакетний запис готового прогону;
executemany частинами по 2 000). Інтеграційні тести storage зелені. Запис першого повного прогону: 1.83 с на
180 рішень, 295 ордерів, 113 позицій, 64 800 точок капіталу (COPY), 26 979 записів ризику, 27 663 записи журналу.

## W-14. Зняття kill-switch: команда з API → воркер
- **Спека (§8.1, API-06):** POST /risk/killswitch/release (admin) → `audit_log`; зняття HALTED — воркером.
- **Зроблено:** джерело правди — `audit_log` (опитування перед кожним баром і кожні 0.5 с у `--linger`), LISTEN
  `fuzzhelm_control` лише будить; застосовуються команди, записані ПІСЛЯ старту сесії, для `run_id` цього прогону або
  без нього; роль актора перечитується з `app_user` (захист у глибину: підроблений запис аналітика в `audit_log` в обхід
  API відхилено — інтеграційний тест). Кожна спроба — запис журналу `control.killswitch_release`.

## W-15. Синтетичні ціни не пишуться в `candle`
Свічки стрес-сценарію живуть лише в журналі прогону (записи `candle`) і подіях SSE: закрита свічка в `candle` більше не
перезаписується жодним джерелом, тож фальшивий обвал назавжди зіпсував би реальну історію. Свічки чистого реплею
пишуться з src = REPLAY (найнижчий пріоритет, існуючих закритих не змінюють).

## W-16. POST /backtests → справжній рушій

## W-17. Шапка «MODE: PAPER · FEED: … · NO MAINNET KEYS · SEED · Q»
MODE — завжди PAPER (виконавець циклу — PaperBroker, ENG-19); FEED — REPLAY або LIVE; «NO MAINNET KEYS» — властивість

## W-18. Перечитування `config/risk_limits.yaml` посеред прогону
Застосовуються лише `limits` і `state_machine`; `sizing`/`hysteresis` — параметри стратегії прогону (входять у
`config_hash`, їх перекривають поля BacktestConfig, напр. `u_enter` профілю replay) — для них потрібен новий прогін.
`run.config_hash` лишається тим, з яким прогін стартував; кожна заміна — запис журналу `control.risk_limits`
(sha256 до/після), невалідний файл — `control.risk_limits_rejected` без зміни стану.

## W-19. Резервне копіювання: `docker compose exec` працює без `.env`
