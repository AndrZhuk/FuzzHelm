# Розходження «спека ↔ реальність»: `exp_analysis` (моделі витрат, ablation, VaR/Купець, гістерезис, таблиці звіту)

Формат: **що в спеці / що насправді / що зробив / чим обґрунтовано**. Числа результатів тут не наводяться — їх дають
повні прогони наступної хвилі закомітченим кодом (`docs/api/exp_analysis.md`).

## XA-01. VaR на вироджених доходностях: «усі бари» і «бари в позиції» — обидва
- **Спека (§5.13):** `r^p_t = ΔE_t/E_{t−1}`, W = 500, VaR₉₅/CVaR₉₅, Купець на пробоях.
- **Насправді:** пласка книга (стратегія більшість часу поза ринком; HALTED/COOLDOWN) дає велику частку `r_t = 0`
  точно. Історичний квантиль вікна з переважно нульовими доходностями = 0, тож «пробоєм» стає будь-який збитковий бар —
  тест Купця на всіх барах міряє частку часу в ринку, а не якість моделі ризику; параметричний σ на такому вікні теж
  вироджений.
- **Зроблено:** `var_backtest.py` рахує все двічі — на всіх барах і на підмножині «бари в позиції»:
  `active_mask`: `pos[t−1] ≠ 0 ∨ pos[t] ≠ 0 ∨ r_t ≠ 0` (позиція на закритті попереднього або поточного бару, або
  капітал змінився в барі — вхід і стоп усередині одного бару, комісія). Для підмножини VaR_t прогнозується на
  останніх W доходностях ПІДМНОЖИНИ (VaR «за умови, що книга в ринку»). У таблиці — частка нулів, частка вікон з
  VaR ≤ 0 і текст, що пояснює, чому результат Купця на всіх барах не про модель.
- **Обґрунтування:** брифінг не визначає, на яких барах валідувати VaR; звітувати лише «всі бари» означало б
  подавати вироджений результат як валідацію моделі, лише «в позиції» — приховати, як поводиться метрика в
  `equity_point`. Показано обидва.

## XA-02. Параметричний VaR як прогноз: σ̂ того самого вікна W, середнє 0
- **Спека:** `VaR = z_{0.95}·σ_p·√h·E` без визначення оцінки σ_p і горизонту бектесту.
- **Зроблено:** `rolling_parametric_var`: `VaR_t = z₀.₉₅·std(r[t−W:t], ddof=1)·√1` — те саме вікно, що в історичному
  прогнозі (однакова кількість прогнозів, та сама вирівнюваність — тест), середнє прийнято 0 (як у формулі брифінгу);
  гроші — множенням на E₀ сегмента. Оцінки на всій вибірці (static) — окремо, як опис розподілу, без тесту Купця.
- **Обґрунтування:** порівняння «історичний vs параметричний» чесне лише за однакової інформації (те саме вікно).

## XA-03. Зведення OOS: зчеплена крива з конкатенованих дохідностей фолдів
- **Спека (§5.16):** таблиця IS/OOS по 6 фолдах; як зводити OOS у одне число — не сказано.
- **Зроблено:** кожен OOS-фолд — окремий прогін з E₀ і NORMAL (протокол `runner.run_walkforward`); зведення:
  `Π(1 + r_t)` конкатенованих дохідностей → Шарп, дохідність, MaxDD; оборот — зважене за барами середнє; комісії й
  угоди — суми; поруч — середнє Шарпів фолдів. Для VaR вікно W на межі фолду бачить кінець попереднього фолду — це
  минуле, а не майбутнє (прогноз лишається «на крок уперед»).
- **Обґрунтування:** одна зчеплена крива — стандартне зведення walk-forward; середнє Шарпів показано, бо на коротких
  фолдах воно може суттєво відрізнятися.

## XA-04. «Наївна модель завищує Sharpe у кілька разів» — лише як вимір, і відношення лише для додатних Шарпів
- **Спека (§5.14, §15):** «Наївна модель без ковзання завищує Sharpe у кілька разів — я це рахую».
- **Насправді:** відношення Шарпів має сенс лише коли обидва > 0; на стратегії з від'ємним Шарпом під повними
  витратами «у k разів» не визначене (знак змінюється або обидва від'ємні).
- **Зроблено:** `compare()` дає різницю, відношення (лише для двох додатних) і ознаку зміни знака; текст висновку в
  `cost_models.md` будується з цих чисел: ПІДТВЕРДЖЕНО — лише при відношенні ≥ 2; інакше звітується різниця / зміна
  знака / «не підтверджено». Типово параметри фіксовані для всіх трьох режимів («та сама конфігурація»);
  `--selection is_grid` додає варіант, у якому і вибір параметрів робиться на кожній моделі витрат окремо.
- **Обґрунтування:** §0.2 — твердження брифінгу перевіряється, а не приймається.

## XA-05. Ablation без VolRegime: V ≡ 0.5
- **Спека (§14 2.11):** «ablation по детекторах».
- **Насправді:** VolRegime не голосує (s = 0), а дає вхід V ядра; без нього V треба чимось задати.
- **Зроблено:** детектор вилучається з набору (`BacktestConfig.detectors`), агрегатор без CONTEXT-виходу бере
  `V_DEFAULT = 0.5` (сподівання перцентильного рангу за відсутності інформації — уже задокументована поведінка
  `decision.aggregator`, DEC-03). У виводі — μ_LO/MID/HI(0.5) з каліброваних МФ: база правил бачить суміш політик.
  Прогрів варіантів однаковий (рахується від повного набору детекторів), тож OOS-сегменти спільні.

## XA-06. κ ≡ 1 через конфігурацію (κ_min = 1), а не обхід коду
- **Зроблено:** `kappa_off`: `detectors.agreement.kappa_min = 1.0` ⇒ `κ = κ_min + (1 − κ_min)·A_g^ν = 1` для будь-якої
  узгодженості; той самий шлях `DecisionCore`, інший `config_hash`.

## XA-07. Ціна гістерезису: компаратор u_exit = u_enter; виміряне число замість «−1.15 %/добу»
- **Спека (§5.9):** «без гістерезису при u ≈ 0.25 позиція перевідкривається щобару: 1440 × 2 × 0.04 % = −1.15 % на
  добу». Арифметика брифінгу хибна на два порядки (R-03: 115.2 % при номіналі N = E).
- **Зроблено:** «без гістерезису» = `u_exit = u_enter` (вихід знаковий, R-09; розмір фіксується на вході, ENG-04 — тож
  додаткові витрати виникають лише з додаткових циклів вхід/вихід). `hysteresis_cost.py` міряє комісії за добу у %
  E₀ з петлею і без, різницю, частоту виконань на бар і номінал виконання/E₀; аналітика §5.9, підставлена з цими
  виміряними величинами, відтворює виміряне (консистентність), а сценарій «2 виконання щобару» при виміряному розмірі
  показує, чому число брифінгу недосяжне. Частка рішень у смузі петлі — `band_stats`.

## XA-08. `--risk-loop relaxed` — ізоляція ефекту від засувки ризику
- **Насправді:** засувка HALTED/COOLDOWN обрізає торгівлю по-різному у варіантах (ті, що швидше палять комісії,
  раніше зупиняються), і «витрати за добу» розбавляються пласкими днями.
- **Зроблено:** опція експерименту: пороги автомата, `max_daily_loss`, `max_drawdown_halt` → 0.93–0.97,
  `warn_vol_ratio` → 1e9 (валідна за схемою `risk.config`). Системна конфігурація не змінюється; у виводі — явна
  позначка. Рекомендовано звітувати обидва прогони (типовий — «як система поводиться», послаблений — «чиста ціна»).

## XA-09. Розбиття `--smoke`
- **Зроблено:** `smoke_folds(n, max_lookback, warmup, k=2)`: `embargo = 2·max_lookback`, `IS = embargo + W + max(100,
  n/10)`, OOS = крок = (n − IS)/2 — ті самі правила (прогрів усередині embargo), але лише для перевірки роботи
  скриптів. Без `--smoke` потрібне повне вікно профілю, інакше — зрозуміла помилка (жодного тихого масштабування).

## XA-10. VaR збереженого прогону (`--run-id`): прогрів відкидається за типовою конфігурацією
- **Насправді:** у рядках БД немає індексу першого рішення.
- **Зроблено (після рецензії):** перша точка вікна оцінки відновлюється ТОЧНО з метрик прогону:
  `decide_from = n_points − 1 − run_metric.n_obs` (рушій рахує `n_obs = len(E) − decide_from − 1`;
  `first_decision_index`); для прогону `89619416-…` це 522, тож на всіх барах n = 64 277 = `n_obs` рушія. Лише без
  `n_obs` — `resolved_warmup() − 1` з позначкою `skip_source` у паспорті. Позиція — `gross_exposure > 0`.

## XA-11. «Ковзання ≈» — відносно P_ref із `Fill.slippage_bps`, з шумом
- **Зроблено:** `Σ qty·price·slippage_bps/10⁴` — ціна виконання проти опорної (open наступного бару / рівень стопа),
  включно з seeded шумом `noise_bps` (EXE-02), тож на малій кількості виконань може бути від'ємним. Позначено «≈»
  (P_ref ≈ price у множнику).

## XA-12. DSR у зведенні — лише проти прогонів сітки на тому самому наборі
- **Спека (§5.15):** N — фактичне число прогонів сітки, Var(SR_i) — по них.
- **Зроблено:** `export_report_tables` рахує DSR стовпця лише з Шарпами (за період) прогонів сітки з тим самим
  `dataset_hash` (БД `grid_cell` або клітинки `full_sr_period` виводу exp_search); інакше — TBD з причиною; DSR самої
  сітки exp_search переноситься дослівно. Групування прогонів у «одну сітку» і лік N — XA-21.

## XA-13. Групи тестів A–N: дослівні назви + евристика файлів
- **Зроблено:** «знайдено дослівно» — точний збіг назви тест-функції (без параметрів); «вузлів» — кейси
  параметризації; «усіх вузлів у файлах групи» — файл належить групі, чиїх дослівних тестів у ньому найбільше
  (позначено як евристику). Заголовок §10 («92 кейси») і сума заголовків груп подаються поруч (D-02).

## XA-14. Таблиця трасування: «підтвердження» — лише наявне
- **Зроблено:** артефакт рядка — лише наявні файли, факти БД і файли результатів; відсутнє — `<<TBD:…>>`: скріншот
  testnet-ордера (EXE-07, крок [ЛЮДИНА]), CRUD правил через UI (UI — окремий етап, D-06), діаграма statechart, вивід

## XA-15. Запис обраної конфігурації в БД — через `DbBacktestRunner`; у цій хвилі не виконано
- **Зроблено:** `plot_equity.py --db --persist` використовує той самий шлях, що й `POST /backtests`
  (`api.backtest_runner.DbBacktestRunner`: паспорт, рушій, `workers.persist`, DONE). Обмеження: передаються лише ключі
  `PARAM_KEYS` API (`n_atr, chi, u_enter, u_exit, rho_base, lam, tp_multiple, cost_mode, initial_equity`) — вибір
  детекторів/`cooldown_policy` так не зберегти. Ідентичність прогону (`ux_run_identity`) не містить `kind`, тож
  клітинка сітки exp_search (kind = grid_cell) з тими самими параметрами на тому самому вікні і з тим самим
  `git_sha` блокує новий запис (`DuplicateRunError`): тоді нічого не пишеться; якщо дубль — `backtest`, крива
  малюється з його рядків `equity_point`, якщо `grid_cell` (кривої в БД немає, XS-04) — з прогону тут же, і
  `equity_hash` звіряється з рядком БД (результат звірки — у виводі).
- **Після рецензії:** шлях запису перевірено на головній БД БЕЗ слідів — `--persist-mode rollback`: той самий
  `DbBacktestRunner` у зовнішній транзакції (кожен `session_scope` раннера — SAVEPOINT, `join_transaction_mode=
  "create_savepoint"`), рядки перечитуються в ній же, наприкінці ROLLBACK. Димово: 3 доби (4 320 точок) і повне вікно
  (64 800 точок, 7.2 с): статус DONE, `equity_hash` рядка = рушій, `config_hash` = очікуваний, `dataset_hash` шляху
  API = завантажувач експериментів; кількості рядків `run/equity_point/risk_event/event_journal/…` до і після —
  однакові. Гілка дубля (очікувана в наступній хвилі: `config_hash` клітинки сітки профілю `grid` = `ea.base_config`
  = `api.build_config` для тих самих параметрів — перевірено; seed і набір ті самі) перевірена одноразовим скриптом у
  відкоченій транзакції: вставлено `grid_cell` з ідентичністю обраної точки → `run_or_duplicate` повертає цей
  `grid_cell`, його `equity_hash` = `equity_hash` прогону тут же. Дубль тепер читається тією самою фабрикою сесій.
  `--persist-mode commit` з незакоміченим кодом — відмова (XA-19).

## XA-16. Бари в позиції можуть не вмістити W = 500
- **Насправді:** частка часу в ринку мала, тож у підмножині «в позиції» доходностей може бути ≤ 500 (що видно вже
  на наявному збереженому прогоні в димовому запуску).
- **Зроблено:** бектест тоді не робиться, причина пишеться в таблицю (жодних чисел замість нього). Опція
  `--window-active N` (типово = `--window`) дає менше вікно лише для підмножини — у виводі це позначено як
  задеклароване відхилення від W = 500.

## XA-17. Робоча точка сітки exp_search обрана за OOS — застереження в кожному виводі зі `--selection fixed`
- **Спека (§5.16):** фронт Парето у критеріях SR_OOS, MaxDD_OOS, Turnover_OOS; робоча точка — з фронту.
- **Насправді:** `run_grid.py` exp_search обирає `choice` за метриками конкатенованого OOS УСІХ клітинок на тих самих
  фолдах (`front_space = "oos"`). Отже `--params @$GRID_S` у cost_models / ablation / var_backtest / hysteresis_cost
  оцінює на OOS точку, обрану за цим самим OOS: це не чиста поза-вибіркова оцінка (вибіркове зміщення; §5.15 враховує
  його через DSR з N = 108), а в ablation зміщення — на користь базової лінії (варіанти оцінюються в точці,
  оптимальній для базової).
- **Зроблено:** `params_source` пише в паспорт походження параметрів (`front_space`, правило, індекс, коміт сітки) і
  `selected_on_oos`; markdown кожного експерименту зі `--selection fixed` і таблиці `export_report_tables` показують
  застереження; stdout — NOTE. Чиста OOS-оцінка — `--selection is_grid` (вибір на IS кожного фолду, окремо для
  кожного варіанта — XA-18); у переліку повних прогонів вона переведена з «необов'язково» в «рекомендовано».

## XA-18. `--selection is_grid`: вибір на IS за правилом фронту Парето, а не argmax SR
- **Було:** `runner.select_cell` (argmax SR → оборот → індекс), тоді як walk-forward exp_search обирає на IS
  ε-обмеженням на фронті (max SR серед клітинок фронту з MaxDD ≤ cool_enter) — дві таблиці «IS→OOS» у звіті
  давали б різні правила вибору, і правило цього компонента суперечило §5.16 («замість argmax Sharpe — фронт»).
- **Зроблено:** `select_on_front` (спільний `backtest.pareto.pareto_front`; код exp_search не імпортується) — те саме
  правило і ті самі тай-брейки, що `choose_from_front` exp_search; `dd_cap` — `cool_enter` системної конфігурації
  (для `--risk-loop relaxed` — теж системної). `--rule sharpe` лишає старий вибір. Правило, фронт і кількість
  допустимих клітинок на кожен фолд — у таблиці вибраних параметрів і `choice_info` JSON. IS-сегмент —
  `[is_start, is_end)` (жодного бару embargo/OOS); клітинка, що змінила б прогрів, → помилка до прогону.

## XA-19. `git_dirty` паспортів — зміни коду, а не виводи; commit у БД лише із закоміченого коду
- **Насправді:** `manifest.read_git_sha` вважає «брудним» будь-який `git status --porcelain`, тож у наступній хвилі
  кожен скрипт після першого бачив би «незакомічені зміни» — власні виводи попередніх кроків (`docs/report_tables/raw`,
  `docs/figures`, `artifacts/exp_search` — не в .gitignore). Прапорець втратив би сенс.
- **Зроблено:** `git_state()` — та сама домовленість, що в exp_search (`GIT_DIRTY_IGNORED = artifacts, docs`):
  `git_dirty` — зміни поза цими каталогами, `git_dirty_any` — сирий, `git_dirty_paths` — що саме (у markdown — перші
  три). `plot_equity --persist` записує в `run_metric.git_dirty` ту саму величину (підклас `DbBacktestRunner` з
  перевизначеним `_git`; API `POST /backtests` не змінено) і в режимі commit відмовляє, якщо код брудний
  (`--allow-dirty` — свідомий обхід, паспорт тоді чесно несе 1).

## XA-20. Оборот зведення OOS — формула `compute_metrics` на зчепленій кривій
- **Було:** зважене за барами середнє оборотів фолдів (`Σ N_k/mean(E_k) · P / Σ n_k`), а документація казала «та сама
  формула, що compute_metrics» — це не так.
- **Зроблено:** `Σ_k N_k·C_k/E_k(0) / mean(E_ланцюга) · P / n` — номінал фолду перемасштабовано з його стартового
  капіталу на капітал ланцюга (так само зводить OOS exp_search, `concat_oos_metrics`); для одного сегмента = оборот
  рушія (тест разом з експозицією).

## XA-21. DSR: N — усі прогони ОДНІЄЇ сітки на тому самому наборі
- **Спека (§5.15):** N — фактичне число прогонів сітки, Var(SR_i) — по них.
- **Було:** N = кількість скінченних Шарпів усіх `grid_cell` на тому самому `dataset_hash` — повторний запуск сітки
  (інший коміт, інший рушій) подвоїв би N і змішав би випробування; клітинка з невизначеним Шарпом випадала з N.
- **Зроблено:** `pick_trial_group` групує `grid_cell` за `(git_sha, seed, engine)` і бере групу з тим самим git_sha і
  рушієм, що в оцінюваного стовпця (інакше найновішу того самого рушія); у виводі — ідентифікатор групи і скільки
  інших сіток є на наборі. `sr0_expected_max`/`dsr_for`: N — усі прогони групи, Var — по скінченних (як у exp_search);
  для скінченних Шарпів збігається з `metrics.dsr` (тест). З виводу сітки exp_search беруться всі клітинки.

## XA-22. Повне вікно BTCUSDT містить вікно калібрування МФ
- **Насправді:** МФ калібровано на днях 1–15 BTCUSDT (`data/dataset_window.json`, `first_is_window`); OOS-фолди
  профілю починаються після них, а область `full` — ні.
- **Зроблено:** заголовок області `full` у всіх таблицях: «для BTCUSDT містить дні 1–15 калібрування МФ — не
  поза-вибіркове». Для ETHUSDT МФ не калібрувались, але і там `full` — не OOS щодо вибору параметрів (XA-17).
