## API-01. Матриця доступу — явна таблиця, роль auditor, додаткові маршрути
- **Що в спеці:** §8.1 задає ролі стовпцем «analyst+» / «analyst (чит.), operator (зміна)» / «admin». Права
  auditor не визначено. Список ендпоінтів §8.1 — мінімальний.
- **Що насправді:** при чотирьох ролях «analyst+» неоднозначне: auditor не «вищий» і не «нижчий» за operator.
  Без власних маршрутів роль auditor нічим не відрізнялася б від analyst.
- **Що зробив:** `api/auth.py: ACCESS_MATRIX` — явна таблиця «дозвіл → ролі» (12 дозволів). Читання доступне всім
  чотирьом ролям. Зміна стратегій дозволена operator і admin. Ліміти й kill-switch — лише admin. Запуск бектесту
  дозволено всім, крім auditor. Журнал аудиту (`GET /audit`) бачать лише auditor і admin. Понад §8.1 додано
  маршрути `GET /auth/me`, `GET /audit`, `GET /runs`, `GET /risk/limits`, `GET /strategies/{name}`,
  `GET /strategies/{name}/versions/{v}`, `POST /strategies/{name}/activate` і `GET /healthz`. Обґрунтування
  кожної клітинки — `docs/security.md` §3.
- **Чим обґрунтовано:** таблицю можна перевірити машинно (параметризований тест: 23 пари «метод × шлях» × 4 ролі)
  і дослівно перенести у звіт (підрозділ 2.9). Розділення обов'язків: аудитор не створює артефактів, які сам же
  перевіряє. Мінімальні привілеї: IP та user_id з аудиту бачать не всі.

- **Що зробив:** ревізія 0004 виконує `ALTER TABLE decision ADD COLUMN sizing JSONB, ADD COLUMN risk JSONB,

  `test_alembic_revisions_form_linear_chain` оновлено. Робочу БД (5442) мігровано до 0004 2026-09-19.
- **Чим обґрунтовано:** зміна адитивна. Нормативні колонки §6 лишилися без змін, а вимогу §8.2 без неї не виконати.

## API-03. Точний множник `risk_event.factor` у `payload.factor_exact`
- **Що в спеці:** `risk_event.factor NUMERIC(6,4)`.
- **Що насправді:** множник SHRINK — точний дріб (`Verdict.factor_dec`, 1e−18). PostgreSQL округлив би,
  напр., 0.99996 до 1.0000, і в журналі SHRINK виглядав би як ALLOW (зауваження рецензента ризику).
- **Що зробив:** колонку лишив за DDL. `RiskEventRepo` дописує `payload["factor_exact"]`, якщо значення не
  вміщується в 4 знаки, а `RiskEventRow.factor_exact` і `GET /risk/events` віддають точне значення.
- **Чим обґрунтовано:** нормативна схема не змінюється, а інформація не губиться
  (`test_risk_event_exact_factor_survives_numeric_6_4`, `test_risk_events_keep_exact_shrink_factor`).

## API-04. `PUT /risk/limits` переписує `config/risk_limits.yaml` (файл — джерело правди)
- **Що в спеці:** «зміна лімітів → `audit_log` (before/after)»; §7: «правила — дані, а не код». Де зберігати
  ліміти, не сказано.
- **Що насправді:** ліміти вже живуть у `config/risk_limits.yaml`, а рушій і воркер читають їх звідти через
  `risk.config.load_risk_config`.
- **Що зробив:** файл перезаписується атомарно (tmp → fsync → `os.replace` → fsync теки, `flock` між процесами).
  Оптимістичне блокування працює за SHA-256 файлу (`expected_sha256` → 409). Аудит (повна конфігурація до і після,
  шляхи змінених значень) пишеться в тій самій транзакції; якщо COMMIT не вдався, файл повертається до попереднього
  тексту. Воркер дізнається про зміну з NOTIFY `fuzzhelm_control` (`risk.limits.changed`). Файл рендериться з
  валідованої моделі, тому зберігається лише **початковий блок коментарів**, решта коментарів губиться, а числа
  записуються як YAML-числа, якщо float точно передає десяткове значення, інакше як рядки.
- **Чим обґрунтовано:** одне джерело правди для API, бектесту й воркера; атомарність і узгодженість з аудитом
  перевірено тестами `test_file_limits_store_atomic_replace_conflict_and_restore` і
  `test_limits_file_restored_when_audit_commit_fails`.

## API-06. Зняття kill-switch через API — команда воркеру (202), а не синхронне зняття
- **Що в спеці:** `POST /risk/killswitch/release` (admin) — «зняття HALTED → audit_log».
- **Що насправді:** автомат станів (`RiskStateMachine`) живе в процесі торгового воркера, у процесі API його немає.
- **Що зробив:** API автентифікує адміністратора (роль перевіряється і за токеном, і за БД), пише `audit_log`
  (`risk.killswitch.release`, before = спостережений стан) і надсилає NOTIFY `fuzzhelm_control`
  `killswitch.release {audit_id, run_id, actor, role}` у тій самій транзакції, відповідь — **202 Accepted**.
  Застосовує команду воркер через `RiskStateMachine.release(Role.ADMIN)`. Пропущені під час простою команди він
  дочитує з `audit_log`. Якщо Telegram налаштовано, API у фоні сповіщає оператора.
- **Чим обґрунтовано:** єдиний власник стану автомата; незмінний аудит — джерело команд, яке переживає рестарти.
  Застосування команди воркером — поза цим компонентом.

## API-07. Джерело SSE — PostgreSQL LISTEN/NOTIFY; авторизація лише заголовком
- **Що в спеці:** `GET /stream/live (SSE)` — «потік подій у браузер». Джерело не задано; задача хвилі вимагає
  обрати, обґрунтувати і зробити тестованим.
- **Що зробив:** воркери викликають `pg_notify('fuzzhelm_live', {"kind","data"})` у своїй транзакції. API тримає
  **одне** з'єднання LISTEN на процес (`PgLiveSource`) і розсилає події через `LiveHub` (обмежені черги,
  кільцевий буфер 512 подій для `Last-Event-ID`, фільтр `kinds`, `max_events`). Payload ≤ 7900 байт, великі
  об'єкти передаються посиланням (`{"kind":"decision","id":…}`). Токен приймається лише в `Authorization: Bearer`,
  тому браузерний клієнт використовує `fetch` + `ReadableStream`, а не `EventSource`.
- **Чим обґрунтовано:** брифінг відкидає брокери (Kafka/Redis), а PostgreSQL уже є. NOTIFY транзакційний: браузер
  не побачить подію, якої немає в БД (`test_sse_streams_only_committed_notifications`). Опитування дало б
  затримку періоду і навантаження ×N клієнтів. `LiveHub` не залежить від PostgreSQL і тестується офлайн. Токен у
  query-рядку потрапив би в журнали доступу.

## API-08. `POST /backtests`: 202, черга в процесі, запис результатів робить API
- **Що в спеці:** «запуск прогону, повертає `run_id`»; контракт задачі припускав, що рушій сам пише результати.
- **Що насправді:** рушій `backtest.engine.run_backtest(dataset, cfg, seed, *, run_id, git, kind) -> BacktestResult`
  чистий (масиви в пам'яті) і БД не знає.
- **Що зробив:** відповідь **202** з `run_id`, прогін іде у фоні (`EngineBacktestService`: ≤ 8 незавершених задач
  → 429, одночасно один, рушій у потоці). Типовий виконавець `api/backtest_runner.DbBacktestRunner` читає свічки
  й фандинг, будує конфігурацію, перевіряє дубль ідентичності, записує паспорт RUNNING, запускає рушій і однією
  транзакцією пише рішення (+ `narrative`), ордери з виконаннями, позиції, капітал, записи ризику та метрики,
  потім `finish(DONE|FAILED)`. Обмеження:
  1. черга не переживає рестарт процесу: прогін, перерваний падінням, лишається RUNNING;
  2. записи `event_journal` прогону не зберігаються (рушій веде журнал з `keep=False`), у паспорті є лише
     `journal_head_hash`;
  3. `git_sha` — HEAD робочого дерева, «брудний» стан у ідентичність не входить;
  4. ідентичний прогін (config, dataset, seed, engine, git) дає задачу FAILED з id наявного прогону;
  5. `strategy_id = null` означає правила й МФ з `config/`, а не «активну» версію;
  6. перші ≈ 523 бари вікна — прогрів.
- **Чим обґрунтовано:** рушій лишається чистим і детермінованим, а читання з БД і запис у БД зосереджено на межі.
  Заміри: 64 800 барів за 6.72–7.01 с при load ≈ 5 (рецензія; будівник: 7.60 с при load ≈ 50), `docs/api/api.md` §5.
  Повний шлях на БД перевіряє
  `test_backtest_runner_persists_run_and_explain_is_consistent`.

## API-09. `/explain` перераховує μ_agg і κ з конфігурації прогону й показує узгодженість
- **Що в спеці:** μ_agg(u) і центроїд «перерахувати детерміновано з MamdaniEngine зі збережених входів і
  конфігурації стратегії прогону».
- **Що зробив:** рушій для перерахунку обирається в порядку достовірності: дерева МФ і правил з
  `run.config.trees` (саме те, що виконував рушій), інакше тексти версії стратегії прогону, інакше `config/`.
  κ_min і ν беруться з дерева detectors прогону. Входи T/R/V перераховуються з точних float JSONB
  `detector_outputs`, бо колонки округлені до NUMERIC(8,5). Блок `consistency` показує, чи перерахунок збігся
  зі збереженим. Розбіжність не приховується, це ознака того, що конфігурацію змінили після прогону. Збережений
  текст `decision.narrative` має пріоритет над перерахованим.
- **Чим обґрунтовано:** поле `strategy.source` показує, звідки відтворено рушій, і пояснення не бреше мовчки.

## API-10. Деталі JWT
- **Що в спеці:** «JWT (HS256, 8 год)»; задача хвилі — claims `sub` + `role`.
- **Що зробив:** крім `sub` (логін) і `role` токен має `uid`, `iat`, `nbf`, `exp`, `iss="fuzzhelm"` і `jti`.
  `exp`/`nbf` перевіряються за ін'єктованим `Clock`, а не за `time.time()` бібліотеки. Оновлення токенів і
  списку відкликання немає: для дозволів зі зміною стану роль перечитується з БД.
- **Чим обґрунтовано:** детерміновані тести без sleep; негайне відкликання прав на зміни без stateful-сесій.

## API-11. Вхід: bcrypt у потоці, обмежувач спроб у пам'яті процесу
- **Що в спеці:** «passlib bcrypt через storage UserRepo».
- **Що насправді:** `UserRepo.authenticate` рахує bcrypt-12 (≈ 0.2 с CPU) синхронно всередині корутини, тобто
  блокує event loop (SSE й інші запити) на кожну спробу входу.
- **Що зробив:** маршрут читає користувача через `UserRepo.get_by_login`, а перевірку пароля
  (`routers.auth.check_password`: та сама семантика, `dummy_verify` для невідомого логіна, > 72 байт → False)
  виконує в `asyncio.to_thread` **поза транзакцією** (рецензія: інакше кожна спроба тримала з'єднання пулу
  ≈ 0.2 с, і серія входів вичерпувала пул для решти запитів); аудит спроби — окремою короткою транзакцією. `LoginRateLimiter` обмежує 10 невдалих спроб за 5 хв на IP і на логін (429).
  Стан обмежувача живе в пам'яті процесу. Невдала спроба пишеться в аудит разом із введеним логіном.
- **Чим обґрунтовано:** перебір паролів не повинен зупиняти сервіс (STRIDE: DoS). Для однієї репліки обмежувача
  в пам'яті досить (залишковий ризик — `docs/security.md` §10).

## API-12. Планувальник — окремий процес; погодинний Q не перезаписує живий
- **Що в спеці:** «APScheduler: нічний добір прогалин, погодинний Q, щоденний звіт».
- **Що зробив:** розклад у UTC: 02:30 — повторний добір PARTIAL/UNFILLABLE (лише для `attempts < 5`; після

  (своєчасність WS), тож його рядки не перезаписуються; REST-добір «запізнілий» за визначенням і в своєчасність
  не входить.

## API-13. `pip-audit`: `ecdsa` 0.19.2 (PYSEC-2026-1325) через `python-jose` — запит, а не зміна
- **Що в спеці:** `pip-audit` у CI і в підрозділі 2.9.
- **Що насправді:** `uv run pip-audit` (2026-09-19) знайшов 1 пакет з уразливістю: `ecdsa` 0.19.2,
  PYSEC-2026-1325 (часова атака Minerva на підпис ECDSA P-256), виправленої версії немає. Пакет транзитивно

- **Що зробив:** нічого в залежностях не змінював (правило хвилі). Токени підписуються лише HMAC HS256, а

  в `docs/security.md` §9.
- **Чим обґрунтовано / запит:** за бажання автора замінити `python-jose` на `PyJWT` (без `ecdsa`). API
  `api/auth.py` ізолює бібліотеку у двох функціях.

## API-15. Набір даних прогону через API будується канонічним шляхом рушія (виправлено на рецензії)
- **Що в спеці:** паспорт прогону (§6 `run`) — тріада відтворюваності `config_hash + dataset_hash + seed` (+ `git_sha`);
  ті самі дані мають давати той самий `dataset_hash`. Рушій фіксує це правило: `Dataset.from_candle_arrays` /
  `with_funding` лишають ставки фандингу з вікна [t₀ − 1 доба, t_last + 1 хв] (docs/api/engine.md §1).
- **Що насправді (знайдено рецензією):** `DbBacktestRunner` сам обрізав ставки до запитаного [ts_from, ts_to) і будував
  `Dataset.from_arrays`. Для повного 45-денного вікна хеш випадково збігався (файл фандингу покриває рівно вікно), а
  для будь-якого під-вікна — ні: дні 10–20 вікна дали 29 ставок проти 32 канонічних, дні 5–6 — 2 проти 5, і
  `dataset_hash` відрізнявся від CLI/сітки/walk-forward на тих самих свічках (скрипт у робочій теці сесії над
  тестовою БД з 64 800 свічками). Наслідки: паспорти API і CLI неспівставні, а перевірка дубля ідентичності
  (`ux_run_identity`) між точками входу не спрацьовує. Крива капіталу при цьому не змінювалася: ставки до першого бару
  рушій на порожню позицію не нараховує.
- **Що зробив:** `prepare_backtest` бере весь файл (`funding_rates(path, instrument)`, замість `funding_arrays`) і будує
  набір `Dataset.from_candle_arrays(arrays, instrument, tf=tf, funding=rates)` — як `backtest.runner.load_db_window`.
  Інтеграційний тест `test_api_dataset_hash_equals_engine_canonical_path_for_subwindow` (синтетичний файл із
  ставками до ts_from, під-вікно 800 барів) падав би на старому коді: ставки до ts_from у набір не потрапляли.
  Повний 45-денний прогін після виправлення дав ті самі хеші й кількості, що й до нього (`docs/api/api.md` §5).
- **Чим обґрунтовано:** одне визначення «набору даних» для всіх точок входу; обрізання — відповідальність рушія.

## API-16. Межі вводу на HTTP-межі: цілі за типами колонок, обсяг обчислень стратегії, текст помилок (рецензія)
- **Що в спеці:** §14 п. 2.9 — «валідація вхідних даних як межа довіри»; задача хвилі — «SQL injection / input
  validation».
- **Що насправді (знайдено рецензією, fuzz на тестовій БД):** цілі параметри не мали верхніх меж. `from_ns=10³⁰` у
  `/market/candles` і `/dq/score`, `seed=2⁷⁰` у `POST /backtests` давали **500**; `instrument_id`, `strategy_id`,
  `version`, `user_id` > INT4 і `decision_id` > INT8 — **503 «database error»** (помилка вводу маскувалася під збій БД);
  `ts_from_ns ≥ 2⁶³` приймався з 202. Окремо `defuzz.grid_nodes` у YAML стратегії обмежений завантажувачем fuzzy лише
  знизу: стратегія з `grid_nodes: 1000000000` зберігалася (201), а перший `/explain` чи бектест з нею вичерпав би
  пам'ять (MamdaniEngine тримає матрицю «терми U × вузли»). Текст помилки прогону (`job.error`, `run.error`, видно в
  `GET /runs/{id}`) для помилок СУБД містив SQL і параметри запиту.
- **Що зробив:** (1) межі `le=INT32_MAX` / `le=INT64_MAX` (типи колонок DDL §6) на всіх цілих параметрах шляхів,
  запитів і тіла `BacktestIn` (`seed ≥ 0`), тепер — 422 з точним `loc`; (2) страховка в обробнику: SQLSTATE класу 22
  (data exception) → 422, а не 503; (3) `validation.check_resource_limits`: `grid_nodes ≤ 2001` (найдрібніша сітка
  дослідження збіжності, Δ = 0.001) і ≤ 15 термів на змінну → 422 з `path`; (4) `backtests.public_error`: для
  `DBAPIError` лише клас і SQLSTATE. Тести: `test_out_of_range_integers_are_422_not_500`,
  `test_database_data_exception_maps_to_422_not_503`, `test_strategy_compute_budget_is_bounded`,
  `test_backtest_failure_text_hides_driver_details`; повторний fuzz на тестовій БД — усі випадки 422.
- **Чим обґрунтовано:** помилка вводу має бути 422 з місцем помилки, а не 5xx; дані з мережі не повинні задавати
  необмежений обсяг обчислень (STRIDE: DoS); деталі драйвера — лише в журнал сервера (STRIDE: Information disclosure).
